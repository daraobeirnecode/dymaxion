# Enterprise Geodatabase: Versioning, Reconcile-and-Post, Backup and Migration

Enterprise (SDE) geodatabases support two multi-user editing models: traditional versioning, where each named version is a lightweight diff against DEFAULT stored in delta tables (A/adds and D/deletes) plus a states tree, and branch versioning, where edits live in the base table with archiving-style rows and all access flows through a feature service on ArcGIS Enterprise — branch is required for Utility Network and Parcel Fabric and is Esri's strategic direction. Reconcile-and-post is how edit versions return home: reconcile pulls DEFAULT's changes into the edit version and surfaces conflicts (by object or by attribute, chosen via conflict definition), post pushes the reconciled result up; automate nightly with `arcpy.management.ReconcileVersions(input_database, "ALL_VERSIONS", "sde.DEFAULT", ..., with_post=True, with_delete=False)` and log conflict counts. Traditional versioning degrades without maintenance: the states tree and delta tables grow until `Compress` (`arcpy.management.Compress`) collapses fully-posted states — the canonical weekly job is reconcile → post → compress → rebuild indexes (`RebuildIndexes`) → `AnalyzeDatasets` for statistics, ideally reaching state 0. Backups must happen at the DBMS layer (`pg_dump`/pgBackRest for PostgreSQL, native backup for SQL Server/Oracle) because SDE metadata tables and data must stay consistent; a geodatabase is not restorable from feature-class exports alone, though periodic FGDB snapshots (`arcpy.management.Copy` or XML workspace export) make good logical fallbacks. Migration between geodatabases (e.g. SQL Server → PostgreSQL, or version upgrades) uses XML Workspace Documents (`ExportXMLWorkspaceDocument`) to carry schema + domains + relationship classes, followed by data copy and `arcpy.management.MigrateStorage` where storage types changed; unversion/re-version around the move and re-register services afterward. GlobalIDs, editor tracking, and archiving (`EnableArchiving`, the `_H` history tables) should be enabled before replication or sync ever touches the data — retrofitting them mid-project breaks replicas. Test restore, not backup: a quarterly restore drill into a scratch instance is the only proof the strategy works.
