## Verdict

The three public cases completed through the production `runSkill` registry, each with two independent live ArcGIS traces, deterministic bundle preview, explicitly approved local persistence, archive read-back, and nine total public REST spot-checks.

The **technical pilot gate passes**:

- all three cases completed in seconds on this machine and network path, below the pilot's ten-minute run ceiling; this is not a production latency or service-level claim;
- all three timestamp-neutral graph hashes matched across independent traces;
- full report and archive hashes differed only because retrieval timestamps and per-run request evidence are intentionally preserved;
- no trace was truncated;
- all three persisted ZIPs matched their preview SHA-256 and byte counts;
- every ZIP contained the full trace report/evidence plus review, evidence manifest, and SVG;
- public serialized approvals remained `[]`;
- all nine deterministic source-reference spot-checks matched public item-data JSON;
- all sampled target item IDs matched public ArcGIS item metadata;
- no item-provided service URL was contacted; and
- a credential-bearing service URL path was detected, removed from output, and represented only as an unresolved reference after remediation.

This does **not** prove customer value, adoption, production suitability, time saved, cost saved, or ROI. No private organization, actual change ticket, independent ArcGIS administrator, or manual comparison baseline was available.

## Observed findings

### Juneau County

- The explicitly “OLD” application resolved to its locked public Web Map.
- The bounded graph exposed 10 direct supported Web Map references, five sanitized service leaves, and one visible owner.
- The graph is small enough to inspect manually and is a plausible retirement/cleanup review input.
- No unresolved references, cycles, or truncation were observed.

### Los Angeles County

- The application resolved to the locked policy/zoning Web Map.
- The bounded graph exposed 30 direct supported Web Map references, 14 sanitized service leaves, and six visible owners.
- This was the largest request footprint in Trace 1: 20 ArcGIS REST requests and 301,088 response bytes.
- No unresolved references, cycles, or truncation were observed.

### Tweed Shire Council

- The application resolved to the locked planning-detail Web Map.
- The corrected bounded graph exposed 32 direct supported Web Map references, 21 sanitized service leaves, and one visible owner.
- One item-provided service URL used an API credential in adjacent path segments. The original trace did not dispatch that URL but serialized it. The pilot spot-check exposed the defect.
- The existing credential detector was extended to reject unambiguous API-key/access-token/client-secret path-pair conventions, including encoded key names, while retaining legitimate services named `token`.
- The final output contains one `credential_bearing_url` unresolved reference and no raw credential value.

## Reproducibility

For every case:

- `trace_structure_hash_matches = true`;
- `trace_report_hash_matches = false`;
- `preview_archive_hash_matches = false`.

This is expected. The timestamp-neutral graph representation was stable, while the full report and archive intentionally preserve `retrieved_at`, request timestamps, and per-run request evidence. Claiming byte-identical archives across independent live retrievals would be false.

The ZIP verifier independently recomputed archive SHA-256 and byte counts and checked the exact four members:

1. `manifest.json`;
2. `report.json`;
3. `evidence.json`; and
4. the case-specific SVG.

The embedded `report.json` contains the concise review, full upstream trace report, and full upstream trace evidence, allowing recipients to recompute provenance hashes rather than trusting orphaned hash claims.

## Manual spot-check

A separate Python verifier selected the runner's deterministic sample of three graph edges per case and fetched only the originating public ArcGIS item-data endpoints. For item edges it also fetched public target item metadata.

Results:

- 9/9 references matched the claimed supported JSON locator;
- every sampled target item ID matched public metadata;
- all requests were anonymous HTTPS requests to the locked ArcGIS portal roots; and
- service URLs were compared as untrusted strings and never contacted.

The verifier required two non-product corrections: support for the documented `baseMap.baseMapLayers[].itemId` locator and exclusion of its own `spot-checks.json` file from the case-record glob. Both were rerun successfully. The first final-rerun attempt also failed before network dispatch because the local command omitted the repository config/workspace overrides; the README now includes them. These are recorded as evidence-workflow friction, not hidden.

## Correction burden

Two material product corrections were required:

1. **Runner integrity correction.** The timed-out draft had a wrong default manifest path, fake DNS override, unlike reference-count comparison, replayed rather than live repeat, an unvalidated numeric risk score, and an archive that omitted full upstream provenance. These were corrected as one pre-acceptance runner redesign.
2. **Credential-path boundary correction.** The public Tweed case exposed a path-segment API credential that was not dispatched but was serialized. The detector, tests, artifacts, and pilot runs were invalidated and regenerated.

The release-gate plan now freezes a ceiling of no more than two additional material corrections after candidate freeze and through the final rerun/release review. The earlier exploratory run did not predeclare that ceiling, so its correction count is descriptive rather than evidence that an original acceptance criterion was met. A third post-freeze material correction changes the verdict to `needs another pilot run`. The security correction is evidence that public-case validation was useful; it is not evidence of production maturity.

Exact-SHA review of blocked candidate `7c4a92717141f1f13ee48f2e3230657e1036964d` required exactly two post-freeze material corrections:

1. reject an explicit default `:443` port from the raw manifest authority before WHATWG URL normalization can erase it; and
2. reconcile the Los Angeles narrative response-byte count to the final Trace 1 record (`301,088`).

The post-freeze ceiling is therefore reached. Any further material correction before release changes the verdict to `needs another pilot run`.

## Value assessment

### What is demonstrated

- On this run and network path, one bounded command assembled a reproducible downstream app → Web Map → item/service review in roughly 1.7–3.9 seconds per live trace for these three public cases; this is not a production latency or service-level claim.
- The output exposes concrete dependencies, visible owners, access metadata, unsupported/missing states, request provenance, and deterministic structure hashes.
- The workflow found a materially important credential-handling defect that synthetic testing had missed.
- The evidence bundle is independently inspectable and suitable as supporting material for a change review.

### What is not demonstrated

- No ArcGIS administrator used the packet on an actual change ticket.
- No manual baseline was timed, so no percentage time-saving claim is valid.
- Public metadata cannot establish complete owner/contact coverage.
- The trace is downstream-only and supports a deliberately narrow set of app/Web Map paths.
- It does not show which other apps consume a target service.
- A human still has to translate the graph into actions, contact owners, assess business criticality, and decide whether a change is safe.

### Honest conclusion

The workflow is **plausibly useful as technical evidence**, but the aggregate findings are still too generic to call it a validated operator product. The raw graph contains the necessary facts; the missing product layer is a concise, confidence-labelled change-ticket checklist that tells the administrator what to review next.

## Next evidence-driven slice

Build an **Actionable Change Ticket Pack** by composing the same eight capabilities and the existing pilot report—no ninth capability and no new item-type parser. The smallest slice should add a deterministic checklist row for each relevant dependency:

- source item and relationship;
- observed owner/access/support state;
- observed vs derived classification;
- explicit confidence/coverage caveat;
- recommended human action such as verify owner, inspect service contract, confirm replacement, or record unresolved credential-bearing reference; and
- direct public source citation.

Then compare that pack with a manual review on one real non-production or approved public change scenario. Stop expansion if it does not reduce the human translation burden or if an administrator does not find it ticket-usable. Reverse-dependency search, more ArcGIS item types, authenticated inventory, and deployment remain frozen until that value gate is met.
